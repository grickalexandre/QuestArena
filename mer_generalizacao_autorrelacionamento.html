Para que serve esta aula

No MER, nem todo relacionamento é “aluno faz matrícula” entre duas entidades diferentes. Duas situações aparecem muito em prova e em projeto:

1. Generalização / especialização

Uma entidade geral se divide em tipos mais específicos. Ex.: Pessoa → Aluno e Professor.

2. Autorrelacionamento

A entidade se relaciona com ela mesma. Ex.: um Funcionário supervisiona outro funcionário.

Ideia-chave Generalização responde: “isto é um tipo de aquilo?”. Autorrelacionamento responde: “isto se liga a outro da mesma coisa?”.

1. Generalização e especialização

Generalização é subir: juntar entidades parecidas em uma entidade-mãe (supertipo).

Especialização é descer: dividir a entidade-mãe em subtipos.

Na prática, o diagrama é o mesmo. Muda só o olhar:

  • de Aluno e Professor para Pessoa = generalizar;
  • de Pessoa para Aluno e Professor = especializar.

Exemplo clássico: Pessoa, Aluno e Professor

Aluno e professor são pessoas. Os dois têm nome, CPF e e-mail. Mas cada um tem dados próprios.

EntidadeO que é comum / próprio
Pessoa (genérica)cpf, nome, data_nasc, email, telefone
Aluno (especialização)ra, curso, serie, data_matricula
Professor (especialização)matricula_funcional, formacao, disciplina
Por que não virar tudo uma tabela só? Porque RA não faz sentido para professor, e formação acadêmica do docente não é dado típico de todo aluno. O supertipo guarda o comum; o subtipo guarda o específico.

Modelo físico, passo a passo

Especialização = relacionamento 1:1. A PK da tabela-filha é a FK para a tabela-mãe (mesmo nome).

PK PessoaId  ----------  FK PessoaId  (1:1)

  1. Tabela-mãe pessoa. PK: PessoaId. Colunas comuns: nome, dataNasc, email.
  2. Tabela aluno: uma coluna PessoaId que é PK e FK → pessoa(PessoaId).
  3. Esse vínculo é 1:1: um aluno é uma pessoa; uma pessoa-aluno aparece uma vez em aluno.
  4. Não crie AlunoId separado: a identidade do aluno é a da pessoa.
  5. Colunas só de aluno: ra, curso, serie.
  6. Tabela professor: PK+FK PessoaId → pessoa (também 1:1). Colunas: formacao, disciplina.
pessoa     (PessoaId PK, nome, dataNasc, email)

aluno      (PessoaId PK+FK → pessoa,  1:1,  ra, curso, serie)
professor  (PessoaId PK+FK → pessoa,  1:1,  formacao, disciplina)

-- PK PessoaId ---------- FK PessoaId     relacionamento 1:1

Um detalhe útil (básico)

Total ou parcial

Total: toda pessoa é aluno ou professor (não existe pessoa “solta”).

Parcial: pode existir pessoa que não é nenhum dos dois (ex.: responsável, visitante).

Use o teste: “X é um tipo de Y?” Se sim, é especialização.

Não confunda com relacionamento comum Aluno cursa Disciplina não é especialização. São entidades diferentes ligadas por um fato. Especialização é quando o subtipo é um supertipo (aluno é uma pessoa).

3. Autorrelacionamento

Autorrelacionamento (ou relacionamento unário) é quando a mesma entidade participa duas vezes, em papéis diferentes.

No diagrama, sai um losango da entidade e volta para ela. Os papéis precisam ter nome, senão o modelo fica ambíguo.

Exemplo clássico: funcionário supervisiona funcionário

Um chefe pode ter vários subordinados (1:N). Um subordinado tem, em geral, um chefe. O chefe também é funcionário: por isso não criamos a entidade “Chefe”.

Modelo físico, passo a passo

  1. Uma tabela só: funcionario.
  2. PK: FuncionarioId.
  3. A FK para o chefe não pode se chamar FuncionarioId (já é a PK). Some o papel: FuncionarioChefeId.
  4. FuncionarioChefeId referencia funcionario(FuncionarioId). NULL = não tem chefe (o diretor).
funcionario (FuncionarioId PK, nome, FuncionarioChefeId FK → funcionario)

Outros exemplos

Exemplo A — 1:1

Pessoa é casada com Pessoa

Papéis: conjuge1 e conjuge2. Cardinalidade 1:1 (modelo simples de casamento civil).

Atributo do relacionamento (opcional): dataCasamento, regimeBens.

Modelo físico, passo a passo

  1. Tabela pessoa. PK: PessoaId.
  2. 1:1 com atributo: crie tabela do relacionamento, por exemplo casamento.
  3. PK: CasamentoId.
  4. Duas FKs para a mesma PK de pessoa — conflito de nome. Use papel: PessoaId (cônjuge 1, copia a PK) e PessoaParId (cônjuge 2).
  5. UNIQUE em cada FK (uma pessoa não casa duas vezes neste modelo simples).
pessoa     (PessoaId PK, nome)
casamento  (CasamentoId PK, PessoaId FK UNIQUE, PessoaParId FK UNIQUE,
            dataCasamento, regimeBens)
Exemplo B — 1:N

Disciplina é pré-requisito de Disciplina

Papéis: disciplina anterior e disciplina posterior.

POO é pré-requisito de Linguagem de Programação I. Modelo 1:N simplificado: cada disciplina tem no máximo um pré-requisito.

Modelo físico, passo a passo

  1. Tabela disciplina. PK: DisciplinaId.
  2. Coluna extra na mesma tabela: FK do pré-requisito.
  3. Não pode se chamar DisciplinaId. Nome com papel: DisciplinaPreId.
  4. NULL = disciplina sem pré-requisito.
disciplina (DisciplinaId PK, nome, DisciplinaPreId FK → disciplina)
Exemplo C — 1:N

Menu contém Menu (submenu)

Um item de menu pode abrir outros itens (Arquivo → Abrir, Salvar). A entidade é a mesma: menu. Papéis: menu pai e submenu. Cardinalidade 1:N. A raiz (menu principal) não tem pai.

Modelo físico, passo a passo

  1. Tabela menu (sem hífen). PK: MenuId.
  2. Colunas próprias: titulo, ordem, url.
  3. FK para o menu pai. Não pode se chamar MenuId. Use o papel: MenuPaiId.
  4. MenuPaiId referencia menu(MenuId).
  5. NULL em MenuPaiId = item da barra principal (não é submenu).
menu (MenuId PK, titulo, ordem, url, MenuPaiId FK → menu)

-- exemplo de linhas
-- 1 Arquivo     MenuPaiId NULL
-- 2 Abrir       MenuPaiId 1
-- 3 Salvar      MenuPaiId 1
-- 4 Editar      MenuPaiId NULL
-- 5 Copiar      MenuPaiId 4
Exemplo D — N:N (peças)

Peça é composta de Peça

Uma bicicleta é composta de quadro, roda, banco. A roda é composta de aro, raio, pneu. Atributo do relacionamento: quantidade.

Modelo físico, passo a passo

  1. Tabela peca. PK: PecaId.
  2. N:N precisa de tabela associativa: pecacomposicao.
  3. PK da associativa: PecaComposicaoId.
  4. Duas FKs para peca. Uma pode copiar a PK: PecaId (conjunto). A outra leva o papel: PecaItemId (componente).
  5. Atributo quantidade fica na associativa.
peca            (PecaId PK, nome)
pecacomposicao  (PecaComposicaoId PK, PecaId FK, PecaItemId FK, quantidade)
Checklist do autorrelacionamento 1) A entidade é a mesma nas duas pontas?
2) Os papéis têm nome claro (chefe/subordinado, pai/filho, origem/destino)?
3) A cardinalidade foi definida (1:1, 1:N ou N:N)?
4) O relacionamento tem atributo próprio? (data, quantidade, resultado)

4. Modelo físico (como vira tabela)

O MER (entidade, especialização, losango) é o modelo conceitual. O modelo físico é o que o SGBD realmente cria: nome de tabela, nome de coluna, PK e FK.

Nesta disciplina usamos esta nomenclatura, sem hífen:

ItemRegraExemplo
Tabela Um nome, minúsculo, sem hífen e sem espaço aluno, professor, carro, pessoa
PK (entidade “solta”) NomeTabela + Id — PK e FK sempre terminam em Id PessoaId, FuncionarioId, MenuId
Especialização PK da filha = FK da mãe, mesmo nome. Relacionamento 1:1 PK PessoaId ---------- FK PessoaId (1:1) em aluno
FK Quando possível, o mesmo nome da PK referenciada Em aluno, a FK para pessoa se chama PessoaId
FK (exceção) Se duas FKs apontam para a mesma PK (autorrelacionamento ou N:N na mesma tabela), o nome igual duplicaria coluna. Aí entra o papel antes do Id FuncionarioChefeId → funcionario.FuncionarioId
Como montar a PK, passo a passo 1. Escreva o nome da tabela-mãe: pessoa.
2. PK e FK terminam em Id: tabela pessoa → PessoaId (sem hífen).
3. Na especialização, a filha não ganha PK nova: usa a mesma coluna como PK e FK (1:1).
Errado: aluno-id, id solto, idPessoa (Id no começo), ou PK AlunoId + FK PessoaId (nesta aula a especialização é PK+FK na mesma coluna).

4.1 Por que a FK copia o nome da PK

Se a PK de pessoa é PessoaId, a FK que aponta para pessoa também se chama PessoaId, salvo conflito de nome.

Na generalização / especialização essa FK é também a PK da tabela-filha. O relacionamento é 1:1:

pessoa.PessoaId (PK)  ----------  aluno.PessoaId (PK + FK)  relacionamento 1:1

4.2 Físico da especialização: Pessoa → Aluno e Professor

Três tabelas. A filha tem uma coluna que é PK e FK: PessoaId. Relacionamento 1:1.

PK PessoaId  ----------  FK PessoaId  (1:1)

Orientador: PK de professor também é PessoaId. Em aluno essa coluna já é o próprio aluno. Use o papel: PessoaOrientadorId (1:N).

CREATE TABLE pessoa (
    PessoaId   INT         NOT NULL,
    nome           VARCHAR(80) NOT NULL,
    dataNasc       DATE        NULL,
    email          VARCHAR(80) NULL,
    CONSTRAINT pkPessoa PRIMARY KEY (PessoaId)
);

CREATE TABLE professor (
    PessoaId INT         NOT NULL,  -- PK e FK, relacionamento 1:1
    formacao     VARCHAR(80) NULL,
    disciplina   VARCHAR(60) NULL,
    CONSTRAINT pkProfessor PRIMARY KEY (PessoaId),
    CONSTRAINT fkProfessorPessoa FOREIGN KEY (PessoaId)
        REFERENCES pessoa (PessoaId)
);

CREATE TABLE aluno (
    PessoaId           INT         NOT NULL,  -- PK e FK, 1:1 com pessoa
    PessoaOrientadorId INT         NULL,      -- 1:N para professor
    ra                     VARCHAR(20) NOT NULL,
    curso                  VARCHAR(60) NULL,
    serie                  VARCHAR(10) NULL,
    CONSTRAINT pkAluno PRIMARY KEY (PessoaId),
    CONSTRAINT ukAlunoRa UNIQUE (ra),
    CONSTRAINT fkAlunoPessoa FOREIGN KEY (PessoaId)
        REFERENCES pessoa (PessoaId),
    CONSTRAINT fkAlunoOrientador FOREIGN KEY (PessoaOrientadorId)
        REFERENCES professor (PessoaId)
);
Leitura linha a linha (aluno) PessoaId — PK e FK. Relacionamento 1:1: PK ---------- FK.
PessoaOrientadorId — FK 1:N para professor (papel, porque PessoaId já existe).
ra, curso, serie — só de aluno.
O que não fazer na especialização Criar AlunoId além de PessoaId.
FK com outro nome (idPessoa, codPes).
Hífen no nome.

4.3 Outro exemplo físico: Veículo → Carro (e autorrelacionamento no carro)

Especialização 1:1: PK+FK VeiculoId. Auto: um carro deriva de outro.

CREATE TABLE veiculo (
    VeiculoId INT         NOT NULL,
    placa         CHAR(7)     NOT NULL,
    ano           INT         NULL,
    cor           VARCHAR(30) NULL,
    CONSTRAINT pkVeiculo PRIMARY KEY (VeiculoId),
    CONSTRAINT ukVeiculoPlaca UNIQUE (placa)
);

CREATE TABLE carro (
    VeiculoId     INT     NOT NULL,  -- PK e FK, 1:1
    VeiculoBaseId INT     NULL,      -- auto → carro(VeiculoId)
    nPortas           INT     NULL,
    airbag            CHAR(1) NULL,
    CONSTRAINT pkCarro PRIMARY KEY (VeiculoId),
    CONSTRAINT fkCarroVeiculo FOREIGN KEY (VeiculoId)
        REFERENCES veiculo (VeiculoId),
    CONSTRAINT fkCarroBase FOREIGN KEY (VeiculoBaseId)
        REFERENCES carro (VeiculoId)
);

VeiculoBaseId aponta para carro(VeiculoId). Não pode se chamar VeiculoId (já é a PK+FK da especialização).

4.4 Físico do autorrelacionamento 1:N (funcionário)

Uma tabela só. A FK aponta para a PK da mesma tabela. Nome da FK = Tabela + Papel + Id (sempre termina em Id).

CREATE TABLE funcionario (
    FuncionarioId      INT         NOT NULL,
    nome                   VARCHAR(80) NOT NULL,
    FuncionarioChefeId INT         NULL,  -- FK para a própria PK
    CONSTRAINT pkFuncionario PRIMARY KEY (FuncionarioId),
    CONSTRAINT fkFuncionarioChefe FOREIGN KEY (FuncionarioChefeId)
        REFERENCES funcionario (FuncionarioId)
);
FuncionarioIdnomeFuncionarioChefeId
1Ana (diretora)NULL
2Bruno1
3Carla1
4Diego2

Ana não tem chefe. Bruno e Carla têm chefe 1. Diego tem chefe 2 (Bruno). A coluna nunca se chama só FuncionarioId duas vezes.

4.5 Físico do autorrelacionamento N:N (peça composta de peça)

N:N gera tabela associativa. As duas pontas são a mesma entidade, então as duas FKs não podem ter o mesmo nome. Uma copia a PK; a outra leva o papel.

CREATE TABLE peca (
    PecaId INT         NOT NULL,
    nome       VARCHAR(80) NOT NULL,
    CONSTRAINT pkPeca PRIMARY KEY (PecaId)
);

CREATE TABLE pecacomposicao (
    PecaComposicaoId INT          NOT NULL,
    PecaId           INT          NOT NULL,  -- peça montada (conjunto)
    PecaItemId       INT          NOT NULL,  -- peça que entra (componente)
    quantidade           DECIMAL(8,2) NOT NULL,
    CONSTRAINT pkPecaComposicao PRIMARY KEY (PecaComposicaoId),
    CONSTRAINT fkComposicaoConjunto FOREIGN KEY (PecaId)
        REFERENCES peca (PecaId),
    CONSTRAINT fkComposicaoItem FOREIGN KEY (PecaItemId)
        REFERENCES peca (PecaId)
);

PecaId na associativa copia a PK (peça-conjunto). A segunda ponta precisa do papel antes do Id: PecaItemId. Quantidade é atributo do relacionamento e fica na associativa — não em peca.

4.6 Mapa rápido: conceitual → físico

No MERNo físico (nossa nomenclatura)
Entidade Aluno (subtipo) Tabela aluno com PK+FK PessoaId (1:1)
Especialização Pessoa → Aluno PK PessoaId ---------- FK PessoaId (mesmo nome, 1:1)
Relacionamento 1:N Professor orienta Aluno Em aluno, FK PessoaOrientadorId → professor(PessoaId)
Autorrelacionamento 1:N FK na própria tabela: FuncionarioChefeId
Autorrelacionamento N:N Tabela extra; uma FK com o nome da PK, a outra com papel
Atributo do relacionamento (quantidade, data) Coluna na tabela que “segura” o relacionamento (lado N ou associativa)
Checklist antes de criar a tabela 1. Nome da tabela: uma palavra, sem hífen (aluno, professor, carro).
2. Entidade “solta”: PK = NomeTabela + Id (PessoaId, MenuId). Sempre termina em Id.
3. Especialização: PK da filha = FK da mãe, mesmo nome. Relacionamento 1:1. Não crie AlunoId.
4. Toda FK tenta usar o nome da PK de destino (também termina em Id).
5. Se o nome da PK já existe na tabela (auto, duas pontas iguais, ou PK+FK da especialização), o papel entra antes do Id: PessoaOrientadorId, MenuPaiId.

10. Aberta — complete o modelo

Uma escola tem Pessoa, com subtipos Aluno e Professor. Um professor pode orientar vários alunos (TCC). Um aluno tem no máximo um orientador.

Tarefa: (1) o que é especialização e o que é relacionamento (cardinalidade); (2) escreva o modelo físico: tabelas, PK, FK e a linha PK ---------- FK (1:1).

Gabarito Especialização: Pessoa → Aluno, Professor.
Relacionamento (não é auto): Professor orienta Aluno, 1:N (1 professor : N alunos). Aluno participa com cardinalidade 0,1 ou 1 (no máximo um orientador).
Não use autorrelacionamento aqui: as pontas são subtipos diferentes, não a mesma entidade no mesmo papel genérico. (Se modelar só Pessoa, aí sim poderia ser auto com papéis orientador/orientando — mas o mais claro é Professor–Aluno.)
Físico: pessoa.PessoaId (PK). Em aluno e professor, PK+FK PessoaId → pessoa (1:1). Orientador (não é especialização): em aluno, FK PessoaOrientadorId → professor(PessoaId).

11. Aberta — invente um autorrelacionamento

No sistema de uma escola, um funcionário treina outro funcionário. Proponha papéis, cardinalidade e um atributo.

Tarefa: escreva o modelo físico (tabela, PK, FK). A FK deve terminar em Id.

Gabarito sugerido Entidade: FUNCIONARIO (tabela funcionario).
Relacionamento: treina / é treinado por.
Papéis: instrutor e aprendiz.
Cardinalidade: 1:N (um instrutor treina vários) ou N:N se houver vários treinamentos.
Atributo: data, tema, cargaHoraria.
Físico 1:N: PK FuncionarioId, FK FuncionarioInstrutorId → funcionario.

12. Aberta — desenhe (no caderno)

Modele:

  1. Veículo com especialização em Carro e Moto;
  2. um carro pode ser “carro-pai” de versões (ex.: Civic → Civic Sport), autorrelacionamento.

Diga se a especialização pode ser parcial (existe veículo que não é carro nem moto?).

Tarefa: desenhe o conceitual e escreva o físico: tabelas veiculo, carro, moto, PK/FK e o autorrelacionamento no carro.

Gabarito sugerido 1) VEÍCULO (placa, ano) → CARRO (n_portas), MOTO (cilindradas). Se o sistema só cadastra carro e moto, especialização total. Se cadastra ônibus também, ou veículo genérico, é parcial.
2) Autorrelacionamento em CARRO: papéis versao_base e versao_derivada, em geral 1:N. Atributo: nome_versao, ano_lancamento.
Físico: tabela veiculo PK VeiculoId; tabela carro PK+FK VeiculoId (1:1); auto: FK VeiculoBaseId → carro(VeiculoId).
São dois mecanismos no mesmo domínio: tipo de veículo (especialização) e família de modelos (auto).

13. Desafio — escolha e justifique

Situação: “Pasta contém pasta” em um drive da nuvem (pasta dentro de pasta).

Isso é especialização ou autorrelacionamento? Cardinalidade?

Tarefa: escreva o físico da tabela pasta (PK e FK, os dois terminando em Id).

Gabarito Autorrelacionamento em PASTA. Papéis: pasta_pai e pasta_filha. Cardinalidade 1:N (uma pasta contém várias; cada pasta filha tem no máximo um pai). A raiz tem pai nulo (relacionamento opcional no papel pai). Não é especialização: a pasta filha não é “um tipo de pasta diferente”; é a mesma entidade em outro nível da árvore.
Físico: tabela pasta, PK PastaId, FK PastaPaiId → pasta(PastaId). Não pode se chamar só PastaId (já é a PK). Sempre termina em Id.

14. Aberta — nomes da PK e da FK

Tabela professor aponta para pessoa. Depois, em funcionario, o chefe é outro funcionário.

Tarefa: escreva PK e FK de cada caso, no padrão da aula (sempre termina em Id).

Gabarito professor: PK e FK PessoaId → pessoa(PessoaId). Relacionamento 1:1 (PK ---------- FK).
funcionario: PK FuncionarioId. FK FuncionarioChefeId → funcionario(FuncionarioId). Aqui não dá para repetir o nome da PK: já existe coluna FuncionarioId.

5.1 Escreva o modelo físico

No caderno, para cada item, entregue:

  1. Nome das tabelas (minúsculo, sem hífen).
  2. Colunas. PK e FK sempre terminam em Id.
  3. Se for especialização: uma coluna só, PK+FK, e a linha PK ---------- FK (1:1).
  4. Se for autorrelacionamento: papel antes do Id (MenuPaiId, não MenuIdPai).
Não copie o exemplo da aula no “piloto automático” Leia o enunciado, monte as tabelas e só depois abra o gabarito.

16. Físico — especialização + relacionamento 1:N

Hospital: pessoa (nome, cpf). Subtipos: paciente (convenio, leito) e medico (crm, especialidade). Um médico é responsável por vários pacientes. Cada paciente tem no máximo um médico responsável.

Tarefa: escreva o físico completo (três tabelas, PK, FK, cardinalidades).

Gabarito Especialização 1:1: Pessoa → Paciente, Medico.
Relacionamento 1:N (não é especialização): médico responsável pelo paciente. 
pessoa    (PessoaId PK, nome, cpf)
medico    (PessoaId PK+FK → pessoa, 1:1, crm, especialidade)
paciente  (PessoaId PK+FK → pessoa, 1:1,
           PessoaMedicoId FK → medico(PessoaId),  1:N,
           convenio, leito)

-- especialização:  PK PessoaId ---------- FK PessoaId     (1:1)
-- responsável:     PessoaMedicoId  (papel antes do Id; PessoaId já é o paciente)
CREATE TABLE pessoa (
    PessoaId INT         NOT NULL,
    nome     VARCHAR(80) NOT NULL,
    cpf      CHAR(11)    NULL,
    CONSTRAINT pkPessoa PRIMARY KEY (PessoaId)
);
CREATE TABLE medico (
    PessoaId      INT         NOT NULL,
    crm           VARCHAR(20) NOT NULL,
    especialidade VARCHAR(60) NULL,
    CONSTRAINT pkMedico PRIMARY KEY (PessoaId),
    CONSTRAINT fkMedicoPessoa FOREIGN KEY (PessoaId) REFERENCES pessoa (PessoaId)
);
CREATE TABLE paciente (
    PessoaId       INT         NOT NULL,
    PessoaMedicoId INT         NULL,
    convenio       VARCHAR(40) NULL,
    leito          VARCHAR(10) NULL,
    CONSTRAINT pkPaciente PRIMARY KEY (PessoaId),
    CONSTRAINT fkPacientePessoa FOREIGN KEY (PessoaId) REFERENCES pessoa (PessoaId),
    CONSTRAINT fkPacienteMedico FOREIGN KEY (PessoaMedicoId) REFERENCES medico (PessoaId)
);

19. Físico — corrija o modelo errado

Um aluno pediu para modelar conta → corrente e poupança. Ele entregou isto:

conta     (id PK, numero, saldo)
corrente  (CorrenteId PK, idConta FK, limite)
poupanca  (PoupancaId PK, cod_conta FK, aniversario)

Tarefa: reescreva o físico no padrão da aula. Liste pelo menos três erros do modelo original.

Gabarito — erros 1. PK id solta (não diz de qual tabela; não segue NomeTabelaId).
2. Filhas com PK nova (CorrenteId, PoupancaId) em vez de reusar a PK da mãe.
3. FK com outro nome (idConta, cod_conta) e hífen/underscore fora do padrão.
4. Especialização 1:1 não aparece: deveria ser a mesma coluna PK+FK. 
conta     (ContaId PK, numero, saldo)
corrente  (ContaId PK+FK → conta, 1:1, limite)
poupanca  (ContaId PK+FK → conta, 1:1, aniversario)

-- PK ContaId ---------- FK ContaId     relacionamento 1:1

20. Físico — os dois mecanismos juntos

Uma publicação (titulo, data) pode ser noticia (fonte, url) ou artigo (doi, revista). Além disso, um artigo pode ser a versão revisada de outro artigo (artigo-base → artigo revisado), 1:N.

Tarefa: escreva o físico. Separe o que é especialização do que é autorrelacionamento.

Gabarito Especialização: Publicacao → Noticia, Artigo (1:1, PK+FK PublicacaoId).
Autorrelacionamento em ARTIGO: um artigo deriva de outro. A PK de artigo já é PublicacaoId, então a FK do artigo-base usa papel: PublicacaoBaseId. 
publicacao (PublicacaoId PK, titulo, data)
noticia    (PublicacaoId PK+FK → publicacao, 1:1, fonte, url)
artigo     (PublicacaoId PK+FK → publicacao, 1:1,
            PublicacaoBaseId FK → artigo(PublicacaoId),
            doi, revista)

-- especialização: PK PublicacaoId ---------- FK PublicacaoId     (1:1)
-- auto:           PublicacaoBaseId  (não pode se chamar PublicacaoId)

21. Físico — CREATE TABLE (laboratório)

Documento de identificação: entidade documento (numero, orgaoEmissor, dataEmissao). Subtipos: rg (uf) e cnh (categoria, validade). Especialização 1:1.

Tarefa: escreva os três CREATE TABLE com PK, FK e o mesmo nome DocumentoId na filha.

Gabarito 
CREATE TABLE documento (
    DocumentoId  INT         NOT NULL,
    numero       VARCHAR(30) NOT NULL,
    orgaoEmissor VARCHAR(40) NULL,
    dataEmissao  DATE        NULL,
    CONSTRAINT pkDocumento PRIMARY KEY (DocumentoId)
);
CREATE TABLE rg (
    DocumentoId INT     NOT NULL,

);
CREATE TABLE cnh (

);

6. Recado rápido para a prova / NSA

  • É um? → generalização / especialização (Pessoa, Aluno, Professor).
  • Liga dois da mesma entidade? → autorrelacionamento (nomeie os papéis).
  • Os dois podem coexistir no mesmo modelo (Veículo se especializa em Carro e um carro deriva de outro carro).
  • Físico: tabela aluno, professor, carro, menu — sem hífen. PK e FK sempre terminam em Id (PessoaId, MenuId). Especialização: PK da filha = FK da mãe (1:1). FK = mesmo nome da PK de destino, salvo conflito (papel antes do Id: MenuPaiId, PessoaOrientadorId).
